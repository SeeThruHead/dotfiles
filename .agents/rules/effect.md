# Effect

- ALWAYS read the Effect repo examples before building with Effect: `~/src/oss/effect` (Effect-TS/effect, `main` is v4; the `v3` branch is v3). effect-smol is archived and merged into it; never reference it. In TRM worktrees the same repo is cloned at `docs/effect` by the worktrunk post-create hook. Verify the API shape against source/tests; don't go from memory. For db/service patterns look at `packages/effect/src/unstable/sql` (SqlClient, SqlModel.makeRepository) and `packages/sql/pg` (PgClient), plus `tools/trm-cli/src/services` in this repo.
- Mainly used in tools/trm-cli; default to not suggesting it elsewhere, but it's allowed in an opted-in spike (e.g. apps/crystal case-investigations + `@trm/effect-drizzle`).
- Use Clock/DateTime services; never Date.now/new Date/Math.random.
- Effect v4: `Effect.catch`, not `Effect.catchAll`. Errors as `Data.TaggedError('Tag')<{...}>` (it IS an Error, so Promise-API-safe + `catchTag` works). Expected failures via `Effect.fail`; unexpected/corrupt data via `Effect.die`/`orDie` (out of the error channel).
- Service = `Context.Service<Self, Shape>()('key')` with `static layer = Layer.effect(Self, Effect.gen(function*(){ const dep = yield* OtherService; return { ...methods } }))`. Yield dependencies ONCE in the layer and close over them. Do NOT yield deps inside every method, and do NOT make a free-floating `ops` object or a `makeX(dep)` factory that takes the dep as an argument.
- Put the method Shape inline in the `Context.Service<Self, {...}>()` generic. `Layer.effect` already checks the returned object against it, so no `satisfies`, no separate `Ops` type alias, no cast. Need the shape elsewhere? Derive it with `Context.Service.Shape<typeof X>`.
- Database = one client service (our `SqlClient`/`PgClient.layer(config)` analog). A repository is an Effect that yields the client once and returns methods. Transactions are a combinator ON the client (`client.withTransaction(effect)`) that swaps the active connection/executor in the fiber context for the body's scope; the repo/service never re-provide themselves. Provide layers + run to a Promise at the composition root (build the method set once).
- Service design: service owns the capability, command/loader is presentation; short pipes, tagged unions, names not ids.
- NO shared/neutral types file, ever (see no-shared-types-file.md). A `Context.Service`'s inline Shape IS the component's public type surface. Do NOT hand-import another service/repo's type aliases to type your own signatures — that couples exactly what DI is meant to decouple. Each component declares its own param/return shapes inline; inline-duplicate a shape rather than share it. Need a dependency's shape? derive it with `Context.Service.Shape<typeof X>`, don't reach for a shared alias. (Genuinely-upstream domain enums/codegen from `@trm/shared`/generated are fine to import; the ban is on hand-authored neutral type modules and cross-component type coupling.)
- Repo errors ≠ domain errors, and they are almost never shared. A repo error is about its persistence process (`XRepoError`) and lives in the repo's file. A service NEVER re-exposes a repo error in its own error channel: it MAPS it into its own domain error (tagged) using the context of the call site (e.g. `applyLock` returning null → `UserNotFound`), or `Effect.die`/`orDie` for a truly unexpected infra fault. Domain errors live in the service's file. Don't lump repo + domain errors into one errors module.
- A service owns its OWN transaction boundary (`client.withTransaction` inside the method that needs atomicity). It must NOT assume/rely on a caller having opened a transaction — nesting composes as a savepoint, so callers can still wrap several service calls atomically.
